## 2. 把嵌套 IR 拆开看

实际 IR 中的第一条 DMA 为：

```python
T.ascend_copy_gm_to_ubuf(
    T.tvm_access_ptr(T.type_annotation("float32"), ub.data, 0, 256, 2),
    T.tvm_access_ptr(T.type_annotation("float32"), src.data, 0, 256, 1),
    0, 1, 1024, 0, 0, 0, 0, 1024, 1024)
```

最里面是类型标记，中间是带访问描述的指针，外面才是 DMA 操作。它们是编译器 IR 的表达式节点，不表示运行时逐层调用普通函数。

以目的指针为例：

| 字段 | 本例值 | 含义 |
| --- | --- | --- |
| dtype | type_annotation("float32") | 地址计算与访问范围按 float32 元素解释；不做数据类型转换 |
| data | ub.data | UB buffer 的底层数据指针 |
| offset | 0 | 从第 0 个 float32 元素开始 |
| extent | 256 | 访问描述包含 256 个 float32 元素，不是 256 字节 |
| rw_mask | 2 | 写访问；源指针的 1 表示读访问 |

可以把它理解为“&ub[0]，并告诉编译器这次会写 256 个 float32”。访问范围与 mask 帮助编译器分析，不会自动产生运行时边界检查，也不是逐元素的 predicate mask。这里只解释连续 dma 用例，不把 extent 当作所有带 stride 用例的完整物理地址跨度。

类比 MLIR：buffer 的 data 类似 memref 的底层指针；offset 类似提取后的元素偏移；读写属性类似操作的 memory effect。TVM 在此把地址和访问描述放进一个 builtin Call 中。这是帮助理解的类比，不是与某个 MLIR op 的一一对应。

源码：[TVM builtin 定义](../../../../../../3rdparty/tvm/include/tvm/tirx/builtin.h#L245)，[copy 构造 access_ptr](../../../../../../src/ascend/op/copy.cc#L208)。

## 3. 外层 11 个参数

| 位置（从 0 开始） | 源码字段 | 本例值 | 含义与单位 |
| --- | --- | --- | --- |
| 0 | dst | ub 的 access_ptr | 写入 UB 的地址 |
| 1 | src | src 的 access_ptr | 读取 GM 的地址 |
| 2 | sid | 0 | 当前 lowering 固定为 0 的底层接口槽位；不是 Kernel 的 bx，也不是 dual_copy 的 AIV sid |
| 3 | nBurst | 1 | 搬 1 个连续数据块；与 Kernel block 数无关 |
| 4 | burstLen | 1024 | 每个数据块的有效字节数 |
| 5 | leftPadding | 0 | 左侧填充的元素数 |
| 6 | rightPadding | 0 | 右侧填充的元素数 |
| 7 | dataSelect | 0 | 映射到 C API 的 enable_constant_pad；本例长度已对齐且无 padding |
| 8 | l2CacheCtl | 0 | L2 缓存管理策略值；不是搬运长度或带宽 |
| 9 | burstSrcStride | 1024 | 相邻源数据块起点的字节间距 |
| 10 | burstDstStride | 1024 | 相邻目的数据块起点的字节间距 |

源码定义：[builtin.h:189](../../../../../../src/ascend/op/builtin.h#L189)。

为什么原来是 4 行，现在 nBurst=1？两边都连续，每行 64×4=256 字节，行起点间距也都是 256 字节，整块可以合成连续的 4×256=1024 字节。只有一个 burst 时，不会访问“下一块”，两个 stride 不会再推动第二次访问；它们不是 1024 字节的额外空洞。

950（3510）这里的 stride 是头到头的间距，与 A2/A3 某些 DMA 接口的尾到头 gap 不同。CANN 本地实现的形参仍叫 src_gap/dst_gap，不能据这个旧名字判断语义。

参数生成：[copy.cc:236](../../../../../../src/ascend/op/copy.cc#L236)，连续合并分支：[copy.cc:304](../../../../../../src/ascend/op/copy.cc#L304)。

## 4. 为什么 kernel.cpp 变短了

对应代码可按下列方式排版理解：

```cpp
asc_copy_gm2ub_align(
    (__ubuf__ uint8_t*)(&(ub[0])),
    (__gm__ uint8_t*)(&(src[0])),
    1, 1024,
    0, 0, 0,
    static_cast<asc_load_l2_cache_mode>(0),
    1024, 1024);
```

- LowerIntrin 将 tvm_access_ptr 变成 address_of，即 &ub[0] / &src[0]，extent 和读写 mask 的分析用途结束。
- 地址空间限定符标记 UB 与 GM；uint8_t* 表示按字节搬运。float32 的位模式原样复制，没有 float→uint8 的数值转换。
- TileLang codegen 去掉固定 sid 槽位，因为这个 C API 不接收 sid；本地 CANN 封装调用底层 intrinsic 时再填固定 0。
- 外层仍然是“1 个连续块，每块 1024 字节”的完整搬运接口，并非调用了只有 size 的三参数重载。

源码：[TVM access_ptr lowering](../../../../../../3rdparty/tvm/src/target/intrin_rule.cc#L129)，[device LowerIntrin](../../../../../../tilelang/engine/lower.py#L93)，[Ascend codegen](../../../../../../src/ascend/codegen/codegen_ascend.cc#L1383)。

## 5. 1024 字节是否可以无限扩大

搬运大小要同时满足接口参数范围、有效 GM 范围、UB 可用容量、地址/长度对齐和依赖同步。带宽是每秒能传多少字节，不能拿它当成一次请求允许的字节数。

当前 950 接口文档给出的 burst_len 范围为 1～2^21−1 字节（2,097,151）。这个字段上限不代表能向 UB 放入约 2 MB：目的 UB 实际容量以及同一 kernel 中其他 buffer 的占用，通常会先形成限制。这里的 1024 字节是有效请求长度，且本例 UB 恰好分配 1024 字节。

UB 起点需要 32 字节对齐；非 32 字节长度可能涉及 UB 补齐空间。真实约束按最终选择的指针 dtype 和接口版本确定，本例 uint8_t 字节搬运、1024 字节已对齐，不涉及额外补齐。上限与约束依据：[官方 3510 接口文档](https://asc.gitcode.com/api/SIMD-API/c_api/vector_datamove/asc_copy_gm2ub_align/asc_copy_gm2ub_align_arch_3510.html)。该站是持续开发版本，不能把全部参数范围直接套到不同本地 CANN 版本。

本地 CANN 9.1.0-beta.3 的 burst 数形参仍为 uint16_t，当前在线文档原型为 uint32_t。这说明即便长度范围相同，也需要按所用版本核对其他字段。本轮没有验证超限输入，也没有证据表明此 TileLang 分支会自动拆分超大请求；不要依赖 CANN 自动兜底。

## 6. CCE 源码之后还有什么

真实设备构建还要由 bisheng 编译 C/C++、内联 CANN 封装并选择设备指令。本地安装的 3510 实现中，uint8_t 重载直接调用 copy_gm_to_ubuf_align_v2，固定 sid=0，没有按 32 字节展开的 C++ 循环。

本地源码追踪：CANN 根目录下 asc/impl/c_api/instr_impl/npu_arch_3510/vector_datamove_impl.h:6296 → vector_datamove_impl/asc_copy_gm2ub_align_impl.h:28 → 第 32 行的底层 intrinsic。没有把 CANN 头文件复制到本仓库。

因此应把本例理解为：提交一个搬运 1024 字节的 MTE2 请求，MTE2 执行后通过 notify/wait 与后续 MTE3 建立依赖。硬件要经过多个传输节拍/存储访问才能完成；一次 DMA 请求不等于一个周期，也不等于一个总线事务。实际拆分粒度与周期数不能从这份 CCE 源码读出；这里没有设备汇编或硬件 trace，因而不声称最终恰好只有一条机器指令。
